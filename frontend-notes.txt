AUTHENTICATION FLOW
===================
1. User enters email & password on login page
2. auth.service.login() validates credentials (mock)
3. If valid:
   - Returns { token, role } where role = "teacher1", "teacher2", or "principal"
   - Token stored in localStorage
   - User object set in AuthContext { email, role }
4. On page refresh:
   - AuthContext calls verifyToken() to restore user session
   - If valid token, user object restored; if invalid, redirected to login
5. Logout clears token and user state


ROLE-BASED ROUTING
==================
Teacher Routes:
  - /teacher1, /teacher2, etc. (dynamic [teacherId] routes)
  - Protected by ProtectedRoute with role matching teacherId
  - Example: Only user with role="teacher1" can access /teacher1/*

Principal Routes:
  - /principal/* (static routes)
  - Protected by ProtectedRoute with role="principal"

Public Routes:
  - /login (no protection)
  - /live/:teacherId (no protection, public viewing)
  - / (redirects based on auth state)

Protection Mechanism:
  - ProtectedRoute component checks if user.role === required role
  - If not authorized, redirects to /login
  - Displays loading state while auth status is being verified


API INTEGRATION APPROACH
========================
Service Layer Architecture:
  ✓ No direct API calls in components
  ✓ All API logic centralized in services/ folder
  ✓ Services are easily replaceable with real backend
  ✓ Mock delays simulate real-world latency

Current Services:
  1. auth.service.jsx
     - login(email, password) → { token, role }
     - verifyToken(token) → { email, role }
     - logout()

  2. content.service.jsx
     - getAllContent() → array of all content
     - getContentByTeacher(teacherId) → teacher's content
     - uploadContent(data) → returns uploaded content
     - approveContent(id) → updates status to "approved"
     - rejectContent(id, reason) → updates status to "rejected"
     - getLiveContent(teacherId) → currently active approved content

API Response Format:
  - Content object: { id, title, subject, description, teacherId, startTime, 
                      endTime, rotationDuration, status, rejectionReason? }
  - Status values: "pending" | "approved" | "rejected"


STATE MANAGEMENT APPROACH
=========================
Tool: React Context API (createContext + useContext)
Reason: Small-to-medium project, no complex nested state

AuthContext stores:
  - user: { email, role } | null
  - loading: boolean (auth initialization state)
  - stats: { total, pending, approved, rejected } (teacher dashboard cache)
  - allStats: { total, pending, approved, rejected } (principal dashboard cache)
  - content: array (teacher's content cache)
  - allContent: array (all content cache for principal)
  - login(email, password) → async function
  - logout() → function
  - resetContext() → clears all caches (called after create/update/delete)

Caching Logic:
  - If data exists in context, skip API call
  - After any mutation (upload, approve, reject), resetContext() is called
  - Components check if cache is null before fetching
  - Prevents unnecessary API calls during same session

ASSUMPTIONS
===========
1. Teacher Identification:
   - Teacher role format: "teacher1", "teacher2", "teacher3", etc.
   - Teacher ID in URL matches their role
   - Example: Teacher with role="teacher1" accesses /teacher1/*

2. Mock Database:
   - lib/data.js serves as in-memory database
   - Data persists during session but resets on page reload
   - Real backend would replace this with actual database

3. Time Scheduling:
   - Uses ISO string format: "2023-01-01T10:00"
   - Content is "active" if current time is between startTime and endTime
   - No complex timezone handling

4. File Uploads:
   - Only accepts JPG, PNG, GIF (image files)
   - Mock service stores file reference, not actual file
   - Real backend would handle file storage (AWS S3, etc.)

5. Approval Workflow:
   - Rejection reason is text-only (no file attachments)
   - Admin can only approve/reject, not edit content

6. Student Access:
   - /live/:teacherId is public (no authentication required)
   - Students see only approved, currently-active content
   - No student login or history tracking
